# ADR-0016: 1.0.0 이후 버전 관리와 릴리스 규칙

- 상태: 채택
- 날짜: 2026-11-25
- 관련: #205(첫 게시, 1.0.0), ADR-0013(웹스토어 업로드), ADR-0014(업데이트 대응), `.github/CONTRIBUTING.md` 5장, `docs/ops/maintenance.md` 3장

## 배경

제품 책임자 결정(2026-11-25): 웹스토어 첫 공개를 **1.0.0**으로 한다. 1.0.0부터는 리팩터링·기능 추가·버그 수정을 체계적으로 묶어 버전을 관리한다.

지금까지는 PR 하나를 병합하면 곧바로 release-please 릴리스 PR도 병합했다. 그래서 2026-11-20~25 닷새 동안 릴리스가 31번 나왔다(0.3 → 0.23). 같은 기간 `feat` 커밋은 54개였고, 형식 데이터 추가 11, solution 9, IDE 7, 백준 연동 7개였다. 개발 단계에서는 문제가 없었지만 공개 뒤에는 다음 문제가 생긴다.

- **웹스토어 심사**: 올릴 때마다 심사가 몇 시간~며칠 걸린다. 심사 중에는 다음 버전을 올릴 수 없다(제출 취소 후 다시 올려야 함).
- **사용자 업데이트**: 브라우저가 업데이트를 받을 때마다 열린 백준 탭의 버튼이 끊긴다(ADR-0014). 잦은 업데이트는 그만큼 사용자를 방해한다.
- **버전의 의미**: 작은 PR마다 마이너가 오르면 버전 번호로 변경의 크기를 읽을 수 없다. 사용자 문의에 "어느 버전부터"를 답하기도 어렵다.

release-please는 **릴리스 PR을 병합할 때만** 버전을 올린다. 그 사이에 병합된 커밋은 하나의 릴리스 PR에 쌓인다. `feat`가 열 개 쌓여도 마이너는 한 번만 오른다. 따라서 문제의 원인은 도구가 아니라 "PR마다 바로 릴리스"라는 운영 방식이다.

## 결정

### 1. 버전 번호 (SemVer, 사용자 관점)

| 올리는 자리 | 언제 | 예 |
|---|---|---|
| **메이저** (`2.0.0`) | 사용자가 하던 일이 더는 안 되거나 저장 데이터를 잃는 변경. 커밋에 `!` 또는 `BREAKING CHANGE:` | 기능 제거, 저장 형식 변경으로 옛 데이터를 못 읽음 |
| **마이너** (`1.1.0`) | 새 기능, 눈에 띄는 동작 변경, 새 언어, 형식 데이터 대량 추가. `feat` | 새 보기, 새 설정, 실행 언어 추가 |
| **패치** (`1.0.1`) | 버그 수정, 성능, 문구·색 조정, 형식 데이터 수정. `fix`, `perf` | 칩 색 수정, 잘못된 형식 고침 |
| 올리지 않음 | `refactor`, `test`, `ci`, `docs`, `chore`, `build`, `style` | 내부 정리 |

- 권한이 늘어나는 변경(브라우저가 사용자에게 다시 허락을 묻고, 그동안 확장을 끈다)은 최소 마이너로 낸다. 릴리스 노트 맨 위에 이유를 적는다.
- `feat(formats)`는 마이너다. 다만 아래 2장의 묶음 규칙 때문에 릴리스마다 한 번만 반영된다.
- 1.0.0은 첫 공개 때 릴리스 PR에 `Release-As: 1.0.0`을 붙여 한 번만 정한다. 그 전까지는 지금처럼 0.x를 쓴다.

### 2. 릴리스는 묶어서 낸다 (1.0.0부터)

- **릴리스 PR은 바로 병합하지 않는다.** 기능·수정 PR은 계속 main에 병합하고, 릴리스 PR에 쌓아 둔다.
- **정기 릴리스**: 버전 마일스톤(아래 3장)의 이슈가 모두 닫히면 릴리스한다. 마일스톤이 길어지더라도 **최소 1주에 한 번까지만** 낸다. 쌓인 것이 패치뿐이면 패치 릴리스가 된다.
- **긴급 패치**: 심각도 S1(잘못 제출, 데이터 손실, 보안)은 그날, S2(핵심 흐름 막힘)는 2일 안에 낸다(maintenance.md 4장). 이때는 쌓여 있던 다른 변경도 함께 나간다. main이 늘 릴리스 가능한 상태여야 하는 이유다.
- **main은 늘 릴리스 가능하게 둔다.** 끝나지 않은 기능은 병합하지 않거나, 사용자에게 보이지 않게(기본 꺼진 내부 플래그) 병합한다. 긴 작업은 작은 PR로 나누되 각각이 깨지지 않아야 한다.
- 릴리스 브랜치와 백포트는 두지 않는다. 웹스토어에는 한 버전만 배포되고, 사용자는 자동으로 최신을 받는다.

### 3. 일을 버전 단위로 묶는다

- **버전 마일스톤**: 다음 마이너를 GitHub 마일스톤 `v1.1`, `v1.2` …로 만든다. 들어갈 이슈를 정하고, 우선순위 라벨(`priority:p0~p2`)로 순서를 정한다. 기능 단위 마일스톤(M0~M7)은 1.0.0까지만 쓴다.
- **패치 마일스톤은 두지 않는다.** 버그는 `type:fix`로 등록하고, 지금 열린 버전 마일스톤에 넣거나 긴급이면 바로 낸다.
- **PR 하나 = 이슈 하나 = 논리적 변경 하나.** 여러 개선은 여러 PR로 나누어 한 릴리스에 묶는다. PR 제목이 곧 변경 기록 한 줄이 된다(스쿼시 병합).
- **리팩터링**은 기능 변경과 섞지 않는다. 별도 `refactor` PR로 내고 동작 변경이 없음을 테스트로 보인다. 버전은 오르지 않지만 다음 릴리스에 함께 나간다.

### 4. 릴리스 절차

1. 마일스톤의 이슈가 다 닫혔는지, main CI가 초록인지 확인한다.
2. 릴리스 PR의 변경 기록을 읽고 사용자에게 보이는 문장으로 다듬는다(한국어, 무엇이 바뀌었는지).
3. 수동 점검표(maintenance.md 5장)를 돌린다. 마이너 이상이면 실제 백준에서 제출 한 번을 확인한다.
4. 릴리스 PR을 병합하면 태그와 GitHub 릴리스, zip이 만들어진다.
5. '웹스토어 업로드' 워크플로를 `publish` 모드로 실행한다(ADR-0013). 심사 중에는 다음 릴리스를 병합하지 않는다.
6. 마일스톤을 닫고 다음 버전 마일스톤을 연다.

### 5. 호환성

- 저장 키나 값 형식을 바꾸면 옛 형식을 **다음 마이너 한 번 동안** 계속 읽고, 그 다음 마이너에서 정리한다. 옮기는 코드는 `runtime.onInstalled`의 정리 단계에 둔다(ADR-0014).
- 메시지 형식(콘텐츠 스크립트 ↔ 서비스 워커)을 바꿀 때는 업데이트 직후의 끊긴 탭(ADR-0014)을 고려한다. 옛 탭은 새로고침 안내만 하면 된다.

## 결과

- 1.0.0 이후 릴리스는 1주에 한 번 이하로 줄어든다. 버전 번호가 변경의 크기를 나타낸다.
- 릴리스 PR이 열려 있는 시간이 길어진다. 릴리스 PR 병합은 정해진 때에만 한다.
- 1.0.0 전(지금)에는 기존 방식(PR마다 릴리스)을 유지한다. 공개 전이라 심사와 사용자 영향이 없고, 각 변경을 바로 압축 해제 설치로 확인할 수 있기 때문이다.
