# ADR-0011: 형식 데이터를 번호 구간 파일로 나눠 필요할 때 읽는다

- 상태: 채택
- 날짜: 2026-11-25
- 관련: ADR-0006(풀이 함수 모드), #116

## 배경

검토한 입출력 형식(ADR-0006의 출처 2)은 `src/data/formats.json` 한 파일에 담겨 IDE 스크립트에 그대로 묶여 있었다. 상위 3,000문제에서 1만 문제, 전체(약 3만 문제)로 넓혀 가므로 크기를 확인했다(2,225문제 기준, 3만 문제는 같은 비율로 늘린 값).

| 방식 | 원본 | gzip | 3만 문제 원본 | 3만 문제 gzip |
|---|---|---|---|---|
| 지금 파일 | 390 KB | 33 KB | 5.1 MB | 433 KB |
| 키를 한 글자로 | 305 KB (−22%) | 32 KB (−4%) | 4.0 MB | 415 KB |
| 키 한 글자 + 기본값(`v`, `cases: null`) 생략 | 274 KB (−30%) | 31 KB (−6%) | 3.6 MB | 409 KB |
| 한 줄 문자열 문법 | 111 KB (−72%) | 26 KB (−20%) | 1.5 MB | 347 KB |
| 한 줄 문자열 + 같은 형식 묶기 + 번호 차이값 | 91 KB (−77%) | 25 KB (−25%) | 1.2 MB | 324 KB |
| 같은 형식 묶기만(고유 1,598개, 72%) | 288 KB | 34 KB | 3.8 MB | 445 KB |

- 확장 패키지는 압축되어 배포되므로 내려받는 크기는 gzip 열을 따른다. 3만 문제여도 0.3~0.45 MB이고, 확장 전체(실행기 런타임 118 MB 포함)에 비하면 작다. 설치 후 디스크 크기도 런타임에 비하면 작다.
- 실제로 비싼 것은 매번 IDE를 열 때다. 묶인 데이터 전체를 스크립트로 읽고, 첫 조회에서 모든 형식을 검사한다. 3만 문제(5 MB)를 데스크톱에서 재 보니 `JSON.parse` 40~60 ms, 검사 70~100 ms였다. 느린 노트북에서는 몇 배가 걸리고, 메모리도 그만큼 쓴다. 문제 수에 비례해 늘어난다.

## 결정

- 형식 데이터를 번호 1,000개 단위 파일 `public/formats/{번호 ÷ 1000}.json`으로 나눈다. 3만 문제면 약 35개 파일이다. 형식은 지금 DSL 그대로 쓰고, 한 문제를 한 줄에 둔다(변경 내역에서 어떤 문제가 바뀌었는지 보이게).
- IDE는 문제를 열 때 그 문제가 든 파일 하나만 `fetch`로 읽는다. 같은 페이지에서 다시 쓰면 기억해 둔 것을 쓰고, 그 문제의 항목 하나만 검사한다. IDE를 여는 비용이 데이터 크기와 상관없이 일정해진다. 확장 페이지 안의 같은 출처 파일이므로 권한이나 `web_accessible_resources`가 필요 없다.
- 키 줄이기나 별도 문법은 쓰지 않는다. 나눠 읽으면 한 번에 읽는 양이 파일 하나(최대 약 170 KB, 한 줄 문자열이면 50 KB)라 이득이 작다. 배포 크기에서의 이득은 gzip 기준 4~25%로 확장 전체에 비해 미미하다. 반면 두 가지 표현, 변환기와 해석기, 그 테스트가 늘고 `formats-reviewed.json`과 출하 데이터의 모양이 달라진다. 3만 문제를 넣은 뒤 패키지 크기가 실제로 문제가 되면 그때 한 줄 문자열 문법(−72%)을 다시 검토한다.

## 결과

- `npm run formats:build`가 `public/formats/*.json`을 만들고, 문제가 없어진 구간의 파일은 지운다.
- `src/solution/bundled.ts`의 `loadBundledFormat(id)`가 파일을 읽고 항목을 고른다. `resolveFormat`은 읽어 온 형식을 인자로 받는다.
- IDE 스크립트에서 형식 데이터가 빠진다.
