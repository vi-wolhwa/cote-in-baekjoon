# ADR-0006: solution 함수 모드

- 상태: 승인 (2026-11-24)
- 관련: M5, #36, PRD 6장 M5

## 배경

프로그래머스처럼 `solution(파라미터) → 반환값`으로 풀게 한다. 백준은 표준 입출력으로 채점하므로, 확장이 문제의 입출력 형식을 알아내 언어별 연결 코드(표준 입력 읽기 → `solution` 호출 → 출력)를 만들고, 코드 실행과 제출 때 사용자 코드에 붙인다.

제품 책임자 결정(2026-11-24):
- solution 함수 모드가 **기본**이다.
- 언어 선택과 같은 줄에 'solution 함수' 켜기/끄기가 있다. 형식을 모르는 문제는 표준 입출력으로 열리고 옵션이 그 상태를 보여 준다.
- 형식 데이터는 **공개 웹의 자료**(블로그, GitHub 풀이 저장소)로 미리 만들어 확장에 넣는다. 공개 자료로 구할 수 없는 문제만 백준에서 느린 속도로 직접 확인한다.
- 사용자 API 키 기능은 넣지 않는다.
- (2026-11-24 검증 후) 형식을 맞추는 일은 확장(개발 쪽)의 몫이다. 문제를 풀려는 사용자에게 JSON 편집, 형식 붙여넣기, 'AI에게 물어볼 프롬프트 복사'를 요구하지 않는다. 편집기는 표 하나(매개변수 추가·삭제 포함)로 두고, 틀린 형식은 '형식 오류 신고'로 받는다. 형식 데이터에서 온 형식에는 출처 배지를 붙이지 않는다.

## 결정

**형식 표기(DSL v1)** — JSON

```json
{
  "v": 1,
  "params": [
    { "name": "n", "type": "int" },
    { "name": "arr", "type": "int[]", "len": "n" }
  ],
  "lines": [["n"], ["arr"]],
  "cases": null,
  "ret": { "type": "int[]", "sep": "\n" }
}
```

- 타입: `int`, `long`, `double`, `string`(토큰), `line`(공백 포함 한 줄), `int[]`, `long[]`, `double[]`, `string[]`, `line[]`(여러 줄을 한 줄씩 통째로), `int[][]`, `long[][]`, `double[][]`, `string[][]`(줄마다 단어 행, 길이가 달라도 됨), `char[][]`
- `lines`: 줄마다 읽을 파라미터. `{ "repeat": "m", "of": "edges" }`로 여러 줄 반복. `line[]`과 2차원 배열은 반복으로만 읽는다
- 개수: 숫자, 앞에서 읽은 정수 이름, `n-1`, `n*m`, `m+k`
- 매개변수가 없으면 입력이 없는 문제다(`solution()`, 입력 반복 없음)
- 개수 없이 끝나는 여러 줄: `{ "until": "0", "of": "nums" }`는 끝내는 줄까지 읽고 끝내는 줄은 값에 넣지 않는다(토큰으로 비교, `line[]`은 줄 전체를 비교해 " ."은 값, "."은 끝). `{ "until": "EOF", "of": "nums" }`는 입력 끝까지 읽으며 입력 반복이 없는 형식의 마지막 줄에만 쓴다. 연결 코드는 행 수를 먼저 세고 같은 방식으로 읽는다
- 개수가 0인 배열은 그 줄이 없어도 된다(빈 줄을 쓰지 않는 문제)
- `cases`: `null`, `{ "count": "T" }`, `{ "until": "EOF" }`, `{ "until": "0 0" }`. 여러 케이스는 케이스마다 `solution`을 부르고 결과를 줄바꿈으로 잇는다
- `ret`: 반환값 출력. 배열 구분자(공백/줄바꿈), 2차원(행 줄바꿈·열 공백), 참거짓 문구, 실수 소수 자리. `line[]`은 원소마다 한 줄씩 그대로(앞 공백 유지) 출력해 별 찍기, `Case #1: …`, 개수 다음 목록처럼 줄마다 모양이 다른 출력을 표현한다
- (2026-11-24 검증 후) 공백이 든 여러 줄, 단어와 수가 섞인 행, 두 덩어리 반복(`m+k`), 입력 없는 문제, 줄마다 모양이 다른 출력을 표현하려고 타입을 넓혔다. 모두 v1에 더한 것이라 이전 형식은 그대로 쓴다

**형식을 정하는 순서** (먼저 있는 것을 쓴다)

| 순서 | 출처 | 화면 표시 |
| --- | --- | --- |
| 1 | 사용자가 저장한 형식 | 직접 정의함 |
| 2 | 확장에 넣은 형식 데이터 | (배지 없음) |
| 3 | 확장 안 추론(예제 토큰 모양 + 입력 설명 문장) | 예제로 추론함 |
| 4 | 없음 → 표준 입출력 | solution 함수 꺼짐, 이유 표시 |

어느 출처든 **예제 검증**을 통과한 형식만 쓴다.
1. 예제 입력을 형식대로 읽어 토큰을 정확히 다 쓴다(개수·타입 일치).
2. 예제 출력을 `ret` 규칙으로 읽고 다시 출력하면 정규화한 기댓값과 같다.
3. 읽은 값을 다시 표준 입력으로 쓰면 원래 예제와 같다(왕복). 이 직렬화로 #36의 파라미터별 테스트 케이스를 표준 입력으로 바꾸고 형식을 검사한다.

**연결 코드** — 정해진 템플릿으로만 만든다(AI가 만든 코드는 넣지 않는다).
- 사용자 코드 뒤에 붙이고, 앞에 붙는 줄(C++ include, Java import)만큼 오류 줄 번호를 보정한다. 식별자는 `__cib_` 접두어.
- 언어마다 연결 코드 파일 하나를 등록한다(ADR-0008). JavaScript: 표준 입력 한 번에 읽기, `console.log` 한 번. Python: `sys.stdin.buffer.read().split()`, `sys.stdout.write`. C++17: `bits/stdc++.h`, 빠른 입출력, 반환 타입을 가리지 않는 출력 템플릿. Java 11: 빠른 입력 리더, 사용자 `class Solution` + 뒤에 `public class Main`.
- 코드는 모드별로 따로 저장한다(모드를 바꿔도 코드가 지워지지 않는다).
- interactive·함수 구현(func) 라벨 문제는 표준 입출력으로만 연다.

**형식 데이터 만들기** (개발 작업, 확장이 하지 않는다)
- 대상 목록: solved.ac 공개 API의 문제 번호·제목·맞힌 사람 수(많이 푼 순).
- 문제 설명은 공개 웹 자료에서 구한다: 공개 GitHub 풀이 저장소(예: 문제 설명을 README에 담는 저장소), 블로그. 각 사이트의 이용 규칙과 속도 제한을 지킨다.
- 풀이 저장소의 **풀이 코드**는 최적이 아니고 남의 코드이므로 그대로 쓰지 않는다(제품 책임자 결정, 2026-11-24). 입력을 어떻게 읽는지 보고 `solution` 파라미터(개수·타입·이름)를 추론하는 참고로만 쓴다. 풀이 코드는 확장·형식 데이터·시작 코드 어디에도 넣지 않고, 커밋하지도 않는다.
- 공개 자료로 구할 수 없는 문제만 acmicpc.net에서 브라우저로 직접 연다: **1분에 1쪽 이하, 하루 상한, 연 기록을 남긴다**. 백준 이용 규칙은 웹 스크래핑을 금지하므로 위반 소지가 있다는 점을 제품 책임자가 알고 결정했다(2026-11-24). 위험은 제품 책임자 계정에 있다.
- 모은 문제 본문은 **로컬에만** 두고(gitignore) 커밋하지 않는다. 확장에는 문제 번호와 형식(DSL)만 넣는다.
- 형식은 같은 추론기로 뽑고 예제 검증을 통과한 것만 넣는다. 추론이 어렵거나 검증에 실패한 문제는 Claude(개발 세션)가 분석해 형식을 쓰고 같은 검증을 거친다.
- (2026-11-24 시범 결과) 검증을 통과한 추론도 검토하면 이름까지 맞은 것이 37%, 구조·타입만 보면 64%였다. 그래서 확장에는 **Claude가 검토한 형식만** 넣는다(`scripts/formats/formats-reviewed.json`, 문제 번호와 형식만). 검토하지 않은 추론은 확장 안에서 '예제로 추론함'으로만 쓴다.
- 시범: 많이 푼 문제 1,000개. 결과(출처별 수, 추론 성공률, 검증 실패 유형)를 보고 범위를 넓힌다. 이 자료는 추론 정확도 평가 세트로도 쓴다.
- (2026-11-24) 제품 책임자 요청으로 상위 3,000문제로 넓힌다. 공개 자료로 입출력 설명과 예제를 모두 모은 문제부터 검토해 넣고, 남은 문제는 공개 자료를 더 찾은 뒤 백준을 하루 상한 안에서 열어 차례로 채운다.

**사용자 형식과 신고**
- 사용자가 고친 형식은 브라우저에 저장한다. 틀린 형식은 '형식 오류 신고'(미리 채운 `4-format.yml` 이슈: 문제 번호, 지금 쓰는 형식, 출처, 버전. 코드·본문 없음)로 받아 확인한 뒤 다음 버전의 형식 데이터에 넣는다.
- 신고 링크에 형식을 `format` 쿼리로 넣으면 GitHub(Rails)가 응답 형식으로 읽어 406을 돌려준다. 필드 id는 `io_format`이다.

## 결과

- 형식을 아는 문제는 바로 함수로 풀고, 모르는 문제는 표준 입출력으로 연다.
- 추론이 틀려도 예제가 적으면 검증을 통과할 수 있다. 화면에 출처를 보여 주고 편집기로 고치게 한다.
- special judge·출력이 갈리는 문제는 로컬 비교가 정확하지 않을 수 있다.
- 연결 코드가 붙은 코드가 백준에 제출되므로 '내 소스'에 연결 코드도 보인다.
