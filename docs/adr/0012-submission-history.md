# ADR-0012: 문제별 제출 기록과 백준 기록 불러오기

- 상태: 채택
- 날짜: 2026-11-25
- 관련: #61(M7 제출 기록), ADR-0002(제출과 채점 결과), ADR-0001(문제 페이지 위 오버레이), ide-spec 7.3

## 배경

제품 책임자 제안(#61): 왼쪽 문제 영역에 제출 기록 탭을 두어 지난 제출의 결과와 코드를 보고, 지난 코드를 다시 불러올 수 있게 한다. 지금은 문제마다 마지막 채점 결과 하나(`judge:{문제}`)만 남고, 제출한 코드는 남지 않는다.

#61의 실현 가능성 분석은 다음과 같다.

1. 확장으로 낸 제출의 코드·결과 기록: 제출할 때 로컬에 저장하면 되고 백준 요청이 없다.
2. 백준에서 직접 낸 과거 제출: 백준 채점 현황을 읽어야 한다. 백준 이용 규칙이 웹 스크래핑을 금지하므로, 사용자가 누를 때 한 페이지만 읽는다.
3. 상위 기록과 비교·분포: 이번 범위에서 뺀다(후속 작업).

## 결정

### 1. 확장 제출 기록 (저장 모델)

- **키**: `storage.local`의 `history:{문제 번호}`. 값은 그 문제의 제출 목록이고 최신순이다.
- **항목**:

  | 필드 | 내용 |
  |---|---|
  | `problemId` | 문제 번호 |
  | `language` | 확장의 언어 id(`python3`, `cpp17` …) |
  | `code` | 백준에 보낸 프로그램 그대로 |
  | `fnCode` | solution 함수 모드(ADR-0006)로 냈을 때 사용자가 쓴 함수. `code`는 여기에 입출력 코드를 붙인 것이다 |
  | `submittedAt` | 제출하기를 누른 시각(밀리초). 문제 안에서 항목을 가리키는 키다 |
  | `result` | 채점 결과: `solutionId`(백준 제출 번호), `status`, `resultCode`, `resultText`, `memoryKb`, `timeMs`. 받기 전에는 없다 |

- **기록 시점**: 백그라운드가 제출 요청(`cib:submit-request`)을 받아 제출 탭을 연 뒤에 항목을 넣는다. 연습 풀이 화면과 모의 시험의 제출이 모두 이 길을 지나므로 한 곳에서 기록한다. 제출 탭을 열지 못하면 기록하지 않는다. 기록에 실패해도 제출은 계속한다.
- **결과 연결**: 채점 현황이 결과를 보고하면(ADR-0002 결정 4) `judge:{문제}`를 쓴 뒤 같은 결과를 기록에도 붙인다.
  - 붙일 항목은 감시(`cib:watch:{문제}`)를 시작한 제출이다. 감시는 제출할 때마다 새로 시작하므로, 감시 시작 시각 1분 전 이후에 기록된 가장 최근 항목을 고른다. 1분 여유는 '결과 다시 확인'이 풀이 화면의 시계로 감시를 다시 시작하기 때문이다.
  - 채점 중 → 최종 결과처럼 같은 제출의 결과는 갱신하고, 이미 붙은 것보다 작은 제출 번호의 보고와 같은 결과의 반복은 무시한다.
- **한도**: 문제마다 최근 **50개**. 넘으면 오래된 것부터 지운다. 코드는 한 항목에 최대 512 KB(기존 제출 한도 `MAX_CODE_LENGTH`)다. `unlimitedStorage` 권한이 이미 있어 저장소 한도에는 걸리지 않지만, 한 키의 값이 너무 커지면 읽고 쓰는 비용이 커진다. 50개면 보통 코드(수 KB)로 수백 KB 안이고, 지난 제출을 다시 보는 데 충분하다.
- **쓰기 순서**: 기록은 한 키를 읽고 고쳐 쓰므로 백그라운드 안에서 한 번에 하나씩 처리한다(모듈 안의 대기열). 서비스 워커가 멈춰도 상태는 저장소에만 있다.
- **검증**: 저장소와 백업 파일에서 읽은 값은 항목마다 검사하고 틀린 항목은 버린다.
- **백업**: `history:{문제}`를 백업·복원에 넣는다. 합치기 복원은 양쪽 목록을 제출 시각으로 합친다(같은 시각이면 지금 것을 남기고, 최신 50개). 요약에 "제출 기록 N개"를 보인다.

### 2. 백준 기록 불러오기 (요청 규칙)

- '제출 기록' 탭의 **백준 기록 불러오기**를 **누를 때만** 요청한다. 탭을 열 때, 풀이 화면을 열 때, 주기적으로는 보내지 않는다.
- **한 번 누르면 한 요청**: 그 문제의 사용자 자신의 채점 현황 첫 페이지 `GET /status?problem_id={문제}&user_id={아이디}`(최근 20개)만 읽는다. 다음 페이지나 다른 문제는 읽지 않는다.
- **간격**: 요청이 진행 중이거나 앞 요청 뒤 3초가 지나지 않았으면 보내지 않고 "몇 초 뒤에 다시 눌러 주세요"를 보인다.
- **누가 보내나**: 풀이 화면은 확장 페이지 iframe이라 `acmicpc.net` 호스트 권한 없이는 직접 요청할 수 없다. 그래서 문제 페이지의 콘텐츠 스크립트가 같은 출처 요청(`fetch`, `credentials: 'same-origin'`)으로 보낸다. 새 권한이 필요 없다.
  - 풀이 화면 → 콘텐츠 스크립트: `postMessage`(`cib:boj-history-request`, 임의 nonce). 콘텐츠 스크립트는 메시지가 자기가 만든 iframe에서 왔는지 확인한다.
  - 문제 번호는 메시지가 아니라 콘텐츠 스크립트가 읽은 문제에서 쓴다.
  - 응답은 확장 출처로만 보내고, 풀이 화면은 백준 출처와 nonce를 확인한다.
- **아이디**: 문제 페이지 머리글의 로그인 아이디(`a.username`, ADR-0005의 `readHandle`)를 쓴다. 없으면 **요청하지 않고** "백준에 로그인하지 않은 상태예요…"를 보인다. 받은 페이지에 로그인 아이디가 없어도(그사이 로그아웃) 같은 안내를 보인다.
- **신뢰하지 않는 입력**: 받은 HTML은 `DOMParser`로 실행·로드 없는 문서로만 만든다. `#status-table`의 행 가운데 그 사용자·그 문제의 행만 골라 결과(ADR-0002의 `parseStatusRow`), 메모리, 시간, 언어(7번째 칸, " / 수정" 링크 앞 이름), 코드 길이(8번째 칸), 제출 시각, 제출 번호만 꺼낸다. 글자 길이와 개수(20행)를 자르고, 풀이 화면이 다시 검사한 뒤 글자로만 보인다. 표가 없으면 "모양이 달라 읽지 못했어요"를 보인다.
- **저장하지 않는다**: 읽은 행은 화면에만 보이고 저장하거나 확장 기록과 합치지 않는다.
- **소스 보기**: 행의 '코드 보기 ↗'는 백준 `/source/{제출 번호}`를 새 탭으로 여는 보통 링크다. 확장은 소스 페이지를 요청하거나 읽지 않는다.

### 3. 화면

- 연습 풀이 화면의 문제 영역에 '문제 설명 | 제출 기록' 탭을 둔다. 자세한 값은 ide-spec 7.3.
- 결과 배지 색은 실행 결과와 같다(맞았습니다 `--pass`, 그 밖의 최종 결과 `--fail`).
- 편집기로 불러오기는 제출의 언어와 모드로 바꾼 뒤 코드를 넣는다. 바뀔 코드가 비었거나 시작 코드나 같은 코드가 아니면 먼저 묻는다.
- 코드 복사는 iframe에서 클립보드 쓰기가 허용되도록 오버레이 iframe의 `allow`에 `clipboard-write`를 더한다. 막히면 코드를 선택해 두고 Ctrl+C를 안내한다.
- 모의 시험 화면에는 탭을 두지 않는다(시험 중 지난 코드를 보는 것은 시험 취지에 맞지 않는다). 시험에서 낸 제출도 기록은 되어 연습 화면에서 보인다.

## 결과

- 확장으로 낸 제출은 코드와 결과가 문제별로 남고, 다시 불러올 수 있다. 백준 요청은 늘지 않는다.
- 백준 기록은 누를 때 한 요청뿐이다. CLAUDE.md의 '사용자 동작 때만 백준에 요청' 규칙 안에 있어 따로 예외를 두지 않는다. 개인정보 처리방침(`docs/privacy.md`)에 요청과 저장 항목을 적었다.
- 백준 채점 현황의 칸 순서(언어 7번째, 코드 길이 8번째)가 바뀌면 그 두 값이 틀린다. 결과·메모리·시간·제출 번호는 기존 선택자(클래스)로 읽으므로 영향이 작다. 합성 픽스처(`tests/fixtures/status-history.html`)로 테스트한다.
- 확인하지 못한 것: 실제 로그인 상태의 채점 현황에서 언어 칸의 정확한 모양(" / 수정" 링크)과 소스 공개 설정에 따른 차이는 공개 자료와 합성 페이지로만 확인했다.
